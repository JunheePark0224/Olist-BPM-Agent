## A. 수동 노트북은 `order_items`를 두 번 조인했다

`05_Root_Cause_Analysis_2.ipynb`는 두 곳에서 같은 테이블을 조인한다.

```python
# cell 3
orders_sellers = orders_delivered.merge(items[['order_id', 'seller_id']], on='order_id')
# → 이미 아이템 단위로 펼쳐짐

# cell 9
orders_sellers_products = orders_sellers.merge(items[['order_id', 'product_id']], on='order_id')
# → 같은 테이블을 한 번 더 조인. 행이 다시 불어남
```

결과:

```
전처리 후 주문           95,082행
 → 1차 조인            108,581행
 → 2차 조인            151,581행   (+43,000행이 복제)
```

이 복제가 통계에 그대로 반영됐다.

| 지표 | 노트북 (이중 조인) | 올바른 단일 조인 |
|---|---|---|
| `product_category` F통계량 | 312.45 | **139.25** |
| `product_category` η² | **12.77%** | **8.35%** |
| `product_weight` r² | 3.39% | 2.27% |

수동 덱(`comparison/manual_v3.pptx`) 슬라이드 7의 헤드라인
**"Product Category η²=12.8%"는 틀린 숫자다.** 실제 값은 8.35%이고,
설명력이 53% 부풀려져 있었다.

### A'. 이것이 조인 때문임을 증명하는 대조군

계산 방식 차이일 가능성을 배제하기 위해, `order_items`를 **거치지 않는**
변수들을 같은 방식으로 비교했다.

| 변수 | 조인 필요? | 노트북 | 파이프라인 |
|---|---|---|---|
| `seller_state` | ✗ | 0.28% | 0.28% |
| `seller_month` | ✗ | 1.51% | 1.51% |
| `seller_dayofweek` | ✗ | 2.45% | 2.45% |
| `product_category` | ✓ | **12.77%** | **8.35%** |
| `product_weight` | ✓ | **3.39%** | **2.27%** |

**조인을 타지 않는 변수는 소수점까지 일치하고, 타는 변수만 어긋난다.**
불일치의 원인이 조인이라는 것이 이것으로 확정된다.

### 파이프라인은 왜 이 버그를 피했나

노트북은 조인을 손으로 타이핑했다. 파이프라인은
[`join_engine.py`](../agent/src/join_engine.py)가 `data_dictionary.json`의 테이블
관계 그래프에서 BFS로 경로를 도출하고, `merged_tables` 집합으로 이미 조인한
테이블을 추적해 재조인을 원천 차단한다.

우연히 맞은 것이 아니라 **조인 경로를 사람 손에서 뺏은 설계** 때문에 맞았다.

⑦ Experiment Design 단계도 같은 방어를 갖는다. 랜덤화 단위 후보를 붙일 때
`order_items`처럼 주문당 여러 행을 갖는 테이블은 `reduce: first`로 축약하고,
병합 전후 행 수가 달라지면 즉시 `ValueError`를 던진다
([`experiment_design.py`](../agent/src/experiment_design.py)의 `attach_cluster_sources`).

## C. 원샷 LLM 덱 — 대체로 맞지만 4개가 틀렸다

CSV를 한 번에 던져 받은 15장 덱은 세 산출물 중 **분석이 가장 깊다.**
거리 반응곡선, ΔR² 블록 투입, ICC/Design Effect, 꼬리 절단(tail truncation)
프레이밍은 수동 덱에도 파이프라인에도 없다. 그리고 이 문서는 그 덱을
깎아내리기 위한 것이 아니다.

**주장 수치 24개 중 21개가 소수점까지 재현됐다.**

| 항목 | 덱 주장 | 재계산 |
|---|---|---|
| 총 리드타임 평균 / 중위 | 12.62 / 10.27일 | 12.62 / 10.27 |
| Carrier 평균 / P90 / P99 / CV | 9.36 / 18.95 / 41.0 / 0.94 | 일치 |
| 구간 비중 | 3.2 / 22.6 / 74.2% | 일치 |
| 상위 10%가 차지하는 Carrier 시간 | 30.5% | 30.48% |
| 지연율, 지연군/정시군 배수 | 8.2%, 3.25배 | 일치 |
| 동일주 34,181건 4.82일 / 타주 11.91일 | — | **건수까지 일치** |
| Cohen's d | 0.877 | 0.877 |
| SP 셀러 아이템 71.3% / 셀러 수 59.7% | — | 일치 |
| Boleto 32.2h / 신용카드 3.9h | — | 32.17 / 3.88 |

그리고 이 덱은 **파이프라인의 η² 값을 독립적으로 재확인해준다** —
고객 주 0.201, 카테고리 0.006, 월 0.056은 파이프라인의 20.19 / 0.68 / 5.77과
같고, 노트북의 12.77%와는 다르다. 조인 버그 판정이 3자 교차검증까지 끝난 셈이다.

### 그런데 리뷰 관련 값은 재현되지 않는다

덱은 슬라이드 2(Executive Summary)와 슬라이드 9에서 이렇게 주장한다.

> **지연 시 1–2점 리뷰 56.7%** (정시 9.4%) · 평균 평점 4.138 · 저평점 비율 13.34%

한 주문에 리뷰가 여러 개 달릴 수 있어 집계 방식을 네 가지로 바꿔 계산했다.

| 집계 방식 | 지연 시 1–2점 비율 |
|---|---|
| 여러 리뷰의 평균 | 54.07% |
| 최저점만 | 54.20% |
| 첫 리뷰만 | 54.10% |
| 마지막 리뷰만 | 54.14% |
| 중복 제거 없음 | 54.1% |
| 지연 정의를 날짜 단위로 | 62.4% |
| **덱 주장** | **56.7%** |

**어느 것도 56.7%가 아니다.** 다섯은 54.1% 부근에 몰리고, 지연 정의를 바꾼
하나만 62.4%로 튀는데 덱의 값은 그 사이에 떠 있다. 평균 평점(4.138 vs 4.154)과
저평점 비율(13.34% vs 12.81%)도 같은 방향으로 어긋난다.

### 왜 이 오차가 위험한가

1. **크기가 하필 위험하다.** 약 5% 차이는 두 배 틀린 것과 달리 아무도
   알아채지 못한다.
2. **가장 많이 인용될 숫자다.** Executive Summary에 박혀 있고, 최종 권고
   ("평균 1일 단축보다 최악 10% 정상화가 평점에 먼저 반영된다")의 근거다.
3. **나머지 21개가 정확해서 더 위험하다.** 대부분 맞으니 나머지도 맞겠거니
   하게 된다.

덱에는 이 밖에도 검증 불가능한 값이 있다. 슬라이드 10의 임팩트 스코어 공식
`|Δ리드타임| × 도달률 × 실행가능성(1–5) ÷ 구현기간`에서 **실행가능성 1~5점은
누가 매겼는지 근거가 없는데 최종 순위를 결정한다.** 슬라이드 11은 세 시나리오
효과를 독립 가정해 단순 합산했고 "과대추정일 수 있다"고 자기 각주로 인정하면서
그 합산값(−17.2%)을 헤드라인으로 쓴다.

## 결론 — 이 판정을 가능하게 한 것

세 방식의 성격이 갈린다.

| | 원샷 LLM | 수동 노트북 | 파이프라인 |
|---|---|---|---|
| 분석 깊이 | **최고** | 낮음 | 중간 |
| 정확성 | 대체로 맞음, 4개 틀림 | **틀림** (조인 버그) | **맞음** |
| 검증 가능성 | **불가** | 어려움 | **가능** |
| 재실행 재현성 | 없음 | 부분 | **있음** |

명제는 "파이프라인이 더 똑똑하다"가 아니다. 그건 사실이 아니다.

> **원샷 LLM은 더 깊은 분석을 더 빨리 낸다. 그런데 그 안의 틀린 숫자를 찾으려면
> 감사 가능한 파이프라인이 필요했다. 내 손 분석의 조인 버그도, LLM 덱의 리뷰
> 오류도 같은 방법으로 찾았다.**

원샷 덱에는 코드도, 중간 산출물도, 어떤 집계 규칙을 썼는지에 대한 기록도 없다.
마지막 줄의 `산출물 생성: pptxgenjs` 한 줄이 전부이고, 다시 돌리면 또 다른 덱이
나온다. **읽어서는 이 오류를 찾을 수 없다.**

이 문서의 모든 판정은 파이프라인이 남긴
[`agent/outputs/processed_dataset.parquet`](../agent/outputs/) 하나로 가능했다.

모델이 더 좋아져도 감사 가능성은 공짜로 생기지 않는다.
